# 我的博客为什么反复搬家

> 2026 年 11 月整理：本文合并了 2020—2022 年的图床、博客同步和 Halo 搭建记录，保留当时的选择与变化。文章沿用原 Halo 稿件的发布日期，所述工具体验均为当时情况。

“离谱，我怎么又开始折腾博客了……”

这是我在 2022 年那篇搭建记录里的开场白。后面还信誓旦旦地说，这是最后一次搞博客。

现在把几篇旧文放在一起看，比起那些已经换过界面的配置步骤，更值得留下的，是每次折腾前的那个问题：我到底想解决什么？

## 先解决写完以后还要搬图片的问题

最开始，我用 Typora 写博客和技术文档。编辑器用得很顺手，但文章里插入的图片，不能跟着文字一起直接搬到博客上。

图片少，重新截图上传就好了。图片一多，写完一篇文章还得再干一遍搬运工的活，实在有点难受。

于是我开始用 PicGo，把图片上传到 GitHub 仓库，再让 Markdown 引用图片地址。选择 GitHub 的理由很朴素：免费，而且我平时就在上面放项目和工作文档，不想为了图床再多维护一个地方。

不过，接上工具不等于一路顺畅。上传失败、端口冲突、文件重名、图片打不开，我在那篇旧文里记了一串问题。有些找到了处理办法，有些当时也没弄明白，只能多试几次。

其中让我印象很深的，是开始学着去看日志。与其看到报错就反复点上传，不如先看看工具到底在说什么。旧教程里的配置会变，这个习惯倒值得留下。

## 能传图片之后，还得让别人看得到

接着遇到的问题是访问体验。

在公司看着还好，回学校想看看博客，或者把文章分享给别人，图片和页面却不一定能顺利打开。于是我尝试过用 CDN 加速图片，也把博客往 Gitee 迁。

但换一个仓库，又带来了新的麻烦：总不能每写一篇文章，都去两个地方更新一次吧？

我当时给自己的要求很明确：依然在 GitHub 写，推送以后自动同步，不增加日常操作。

手动点同步当然可以，分别向两个仓库推送也可以，可这都没有满足我想少做一步的需求。后来我试了 GitHub Actions，按参考项目配置工作流，把同步这件事交给它去跑；2022 年又在原文补充了当时 Gitee 镜像管理的做法。

那次折腾让我第一次觉得，自己的博客也可以当成一个小产品来改进。需求很小——少点一次按钮，少维护一份内容——但为了实现它，我接触到了以前没用过的自动化工具。

当然，旧文里也留着我当时没完全理解的配置原理。这些学习中的问号，没必要在复盘时装作早就懂了。

## 从坚持免费，到愿意为爱好花一点钱

到了 2022 年，博客和图片的稳定性还是让我不满意。我终于决定：买服务器，买对象存储，再换一次方案。

那次选了 Halo，图片放到腾讯云 COS。吸引我的并不只是“又发现了一个新框架”，而是几个很具体的点：

- 页面看着清爽，自己愿意打开。
- 支持导入 Markdown，不用为了发布重新搬一遍正文。
- 当时试用的流程图展示符合我的需要。
- 技术栈是 Spring Boot，我想着以后也许还能自己改一改。

迁图片时，我把旧图床里的文件打包搬到对象存储，再调整文章里的地址。换博客并不只是把一个服务装起来，旧文章和图片能不能跟过去，也得一起考虑。

这次还有一个挺明显的变化：之前总觉得，能免费就不花钱；正式工作以后，我开始觉得，为自己的爱好花一点钱也可以接受。省下反复处理访问和图片问题的精力，才有心情继续写。

这只是我当时的选择。它不能证明付费方案一定更好，也不能证明那次迁移就解决了以后所有的问题。

## 折腾留下的东西

把这些记录连起来看，每次迁移都有一个具体的起因：图片搬运麻烦、访问不顺、重复维护、发布步骤太多。

早期我很容易把“搭好了”当作完成。真正用起来才会发现，写作、上传、访问和迁移，是一整条链路。某一处顺了，别处也可能冒出新的麻烦。

我在同步教程的结尾写过：有了需求，才会推动自己尝试方法、学习知识。博客正好是一个很小、又能一直用下去的练习场。

所以，这次把几篇旧教程收成一篇，不再把每一个安装界面都重新讲一遍。留下当时为什么选、哪里不顺、后来怎么改，已经足够说明这段折腾的意义。

至于“最后一次搞博客”这句话，就留给 2022 年的我吧。那篇文章里另一句话，更适合一起留下：无论什么样的博客都只是一个展现的形式，还是应该专注于内容的创作。
